ROP014 | SCOPED, NOT YET BUILT | Region-level destination (Falcon, SES020 close-out, captured verbatim so it isn't lost to context): sometimes a client has no particular place in mind, just a general area — Falcon's example is "CARAGA" (an actual `provinces.region_name` value already driving Tier 2 in `computeTier()`, ROD009/existing Rate Matrix). Design, locked via multiple rounds of Q&A this session:
  (1) Picker — every real PH region is individually searchable (not just 3 generic Tier options), surfaced as just another result *inside* the existing `HybridLocationSearch.tsx` box alongside real place-name matches (typing "Caraga" shows both actual places named that AND the CARAGA region option, side by side). No separate control.
  (2) Resolution — picking a region resolves to a "representative point": the *farthest* province/city within that region from HQ (a worst-case distance, not average/nearest), computed dynamically off HQ's actual geocoded location — explicitly NOT hardcoded per region name/business, since Falcon wants this to work for any business's HQ location on RACOS, not just this one. That resolved province_id/city_id gets written to `bookings.destination_province_id`/`destination_city_id` as normal (no schema nullability change) but flagged/labelled as a representative pick — e.g. a note/badge reading "Representative point" wherever it's displayed (booking form, Summary, Map popup, etc.) — so it stays visually/structurally distinguishable from a client's actual named-place pick everywhere destination is read (Map destination-history, GPS corroboration, Analytics top-destinations).
  (3) Tier — since it resolves to a real province in the picked region, `computeTier()` runs completely unchanged: same region as HQ → Tier 2, different region → Tier 3. Tier 1 (same province as HQ) is never reachable via a region-only pick by definition — confirmed correct by Falcon.
  (4) Pricing — no new pricing logic needed at all; Rate Matrix already prices off the resulting Tier exactly as it does today (Falcon: "the pricing was already handled here based on the rate matrix logic").
  (5) Verification — Falcon explicitly does not want a corroboration workaround built for this: the real, actual destination is verified after the fact through the existing GPS Log (automatic Traccar or manual entry) the same way any other booking already is (ROD028) — the region pick is only ever a *declared-at-booking-time* placeholder, real-world tracking is unaffected and untouched.
  Still open before build: the exact algorithm for "farthest point in region from HQ" (province-level only vs. municipality-level; live-geocode-and-cache like the existing Nominatim pipeline, or precomputed) — an implementation detail to work out at build time, not a design question left for Falcon.
