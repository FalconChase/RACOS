| RC006 | HIGH | Two new migration files (0019, 0020) were added to src-tauri/migrations/ but never registered in src-tauri/src/lib.rs's hand-maintained `local_db_migrations()` Vec — this project does not auto-discover migration files from the folder, each one needs its own explicit `Migration{}` entry. Both silently never ran. Symptom: every Settings toggle failed outright once `auto_mark_departed` was referenced in the shared updateSettings() query against a column that didn't exist; retroactively, this also means every "cancelled"/"completed"/"departed" action_logs insert had likely been failing too, since the widened CHECK constraint from 0019 never applied either. | SES009 | FIXED — FX006 |
| RC007 | HIGH | gps-ingest's device-matching logic checked Traccar's `position.deviceId` (internal numeric DB id) before `device.uniqueId` (the real string identifier, e.g. "STAGE1TEST") in a `??` fallback chain. Since the numeric field is never null, it always won, so every real Traccar-forwarded position 404'd as "no vehicle found" even though the vehicle was registered correctly. Only surfaced with a real Traccar payload during Stage 1 — Stage 0's fake curl test didn't have this field ambiguity. | SES010 | FIXED — FX007 |
| RC008 | MED | LoginScreen's internal `mode` state was seeded via `useState(initialMode)`, which React only reads on first mount. Symptom: sign-in appeared to do nothing when clicked, even though Supabase had recorded a successful login (confirmed via auth.users.last_sign_in_at). | SES012 | FIXED — FX008 |
| RC009 | MED | lib/db.ts's session state (`_businessId`/`_profileId`) is plain module-level `let`, not React state. Symptom: Home/Settings hung on "Loading…" forever after a live code edit mid-session, with zero error feedback (no fetch chain had `.catch()`). | SES013 | FIXED — FX009 |
