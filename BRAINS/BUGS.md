# RACOS persistent bug register. BUG IDs are ecosystem-wide (RC001). Empty at GAP onboarding (GA004).

| ID | SEVERITY | ITEM | FOUND | STATUS |
|----|----------|------|-------|--------|
| RC001 | MED | SearchableSelect rendered a full-screen invisible click-catching overlay while open. A click meant for another button elsewhere on the page (e.g. Settings "Save") landed on the overlay instead of its target, closing the dropdown and swallowing the click. Affected every screen using the component. | SES006 | FIXED — FX001 |
| RC002 | HIGH | business_profile.hq_city_id / custom_rates.city_id / bookings.destination_city_id still declared `references cities(id)` after migration 0008 dropped the `cities` table. The app's real tauri-plugin-sql (sqlx) runtime enforces foreign keys — unlike the Python sqlite3-module dry-run used to verify migrations — so any write to those columns failed at runtime with "no such table: main.cities". Symptom: HQ province/city (and by extension custom rates / booking destinations) silently couldn't be saved. | SES006 | FIXED — FX002 |
| RC003 | HIGH | None of the new Registry/Vehicle-edit save handlers (VehicleOwnerForm.handleSubmit, OwnerEditRow.handleSave, VehicleEditRow.handleSave) had try/catch. Any thrown DB error rejected silently with zero UI feedback. Symptom: "I can't register the owner and vehicle, nothing happens when I click Register." | SES007 | FIXED — FX003 |
| RC004 | HIGH | Migration 0010_owners.sql was edited (to add a CHECK-constraint value) after it had already been applied to the user's local db. tauri-plugin-sql's per-migration checksum no longer matched, so on relaunch it rejected all migrations and the whole db connection hung. Symptom: app stuck forever on "Starting up…", console showing "migration 10 was previously applied but has been modified," and every DB-backed action (including RC003's Register button) appearing broken since nothing could ever finish connecting. | SES007 | FIXED — FX004 |
| RC005 | HIGH | Remittances breakdown blocks initially split a booking's payment into two independent buckets (scheduled hours vs. overtime hours) instead of one shared bucket. Reconciled fine for simple cases but gave the wrong amount for any block straddling the overtime boundary — verified wrong against the user's reference PDF (scenario 3: computed 2500 for a 24h block that should bill a clean full-rate 2400), since a block could bill against "overtime money" an earlier block had already spent. | SES008 | FIXED — FX005 |
| RC006 | HIGH | Two new migration files (0019, 0020) were added to src-tauri/migrations/ but never registered in src-tauri/src/lib.rs's hand-maintained `local_db_migrations()` Vec — this project does not auto-discover migration files from the folder, each one needs its own explicit `Migration{}` entry. Both silently never ran. Symptom: every Settings toggle failed outright once `auto_mark_departed` was referenced in the shared updateSettings() query against a column that didn't exist; retroactively, this also means every "cancelled"/"completed"/"departed" action_logs insert had likely been failing too, since the widened CHECK constraint from 0019 never applied either. | SES009 | FIXED — FX006 |
| RC007 | HIGH | gps-ingest's device-matching logic checked Traccar's `position.deviceId` (internal numeric DB id) before `device.uniqueId` (the real string identifier, e.g. "STAGE1TEST") in a `??` fallback chain. Since the numeric field is never null, it always won, so every real Traccar-forwarded position 404'd as "no vehicle found" even though the vehicle was registered correctly. Only surfaced with a real Traccar payload during Stage 1 — Stage 0's fake curl test didn't have this field ambiguity. | SES010 | FIXED — FX007 |
| RC008 | MED | LoginScreen's internal `mode` state was seeded via `useState(initialMode)`, which React only reads on first mount. When App.tsx changed the `initialMode` prop from "signin" to "complete-profile" after a successful sign-in with no profile row yet, React reused the already-mounted instance instead of remounting it, so the prop change was silently ignored. Symptom: sign-in appeared to do nothing when clicked, even though Supabase had recorded a successful login (confirmed via auth.users.last_sign_in_at). | SES012 | FIXED — FX008 |
| RC009 | MED | lib/db.ts's session state (`_businessId`/`_profileId`) is plain module-level `let`, not React state. Vite Fast Refresh preserves component state across live edits but re-executes changed modules' top-level code, silently resetting these to null while the UI still showed the authenticated shell. Symptom: Home/Settings hung on "Loading…" forever after a live code edit mid-session, with zero error feedback (no fetch chain had `.catch()`). | SES013 | FIXED — FX009 |
